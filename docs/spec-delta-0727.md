## 0. 한눈에

가장 큰 변화 셋.

나머지는 위 셋의 파생이거나, G2 이후에 부딪힐 문제를 미리 정해둔 것이다.

## 1. 제품 정체성 `[정체성]`

### 1-1. 강점 서술 교체

README 첫 문단의 다나와 비유는 유지한다. 다만 제품의 강점을 아래 셋으로 **명시**한다.

| | 무엇 | 답하는 질문 |
|---|---|---|
| **정의권** | 세상에 없는 카테고리를 사용자가 만든다 | 왜 필요한가 |
| **원문 대조** | 자동으로 모았지만 원문으로 확인할 수 있다 | 믿을 수 있는가 |
| **지속** | 한 번 만들면 살아서 갱신된다 | 왜 API 인가 |

**"자유도"라는 표현은 쓰지 않는다.** 범용 도구가 전부 주장하는 말이라 아무 그림도 만들지 못하고,
"아직 안 정했다"로 읽힌다. 자유도는 위 셋을 가능하게 하는 수단이지 강점 자체가 아니다.

한 문장 정의:

> 세상에 없는 카테고리를, 원문까지 확인 가능한 상태로, 계속 살아있게 만드는 도구.

### 1-2. 원문 대조의 위상 상승 `[변경]`

현재 README 에서 G2 의 한 줄 항목("원문 대조 (값 → 원문 조각)")으로 있다.
**강점 #2 로 승격**한다. LLM 이 컴파일한 어댑터의 값은 기본적으로 신뢰할 수 없고,
통합 서비스에서 신뢰가 깨지면 사용자는 원본 사이트로 돌아간다. 정의권과 세트로 가야 완결된다.

### 1-3. 대상 사용자 `[결정필요]`

`endpointer` 라는 이름과 REST/MCP 는 개발자를 가리키는데,
보장선 B1~B7 과 화면 문자열 내부 명사 점검(ADR A26)은 비개발자를 겨냥한다.

둘 다 존재하는 건 설계 의도(표는 사람이, API 는 코드가)라 문제는 아니다.
다만 **온보딩과 발표는 한쪽을 앞에 세워야 한다.** 강점이 정의권이면 비개발자가 앞이고,
그 경우 MCP 는 마지막 각주로 내려간다. 제품명도 재검토 대상(가칭이므로).

## 2. 뷰(View) — 신규 도메인 개념 `[신규]`

**이번 논의의 최대 추가.** 기존 "구독"을 흡수하고 확장한다.

### 2-1. 정의

> 뷰는 **"내가 계속 신경 쓰기로 한 것"의 정의**다.

한 문장으로 표현하면:

> 이 컬렉션에서 **○○인 것**을 **△△ 순**으로 보고, 새로 생기면 **□□로** 알려줘.

### 2-2. 구성 요소

```jsonc
{
  "slug": "deadline-soon",              // 이름에서 자동 생성. API/MCP 에서 참조
  "name": "이번 달 마감 · 대학생",        // 조건에서 자동 제안, 수정 가능
  "where": [                            // ★ 사용자가 정해야 하는 유일한 필수 항목
    { "field": "deadline", "op": "within",   "value": "this_month" },
    { "field": "target",   "op": "includes", "value": "대학생" },
    { "field": "prize",    "op": "gte",      "value": 1000000 }
  ],
  "sort":    [{ "field": "deadline", "dir": "asc" }],   // 기본값 있음
  "columns": ["title", "source", "deadline", "prize"],  // 기본값 = 컬렉션 기본
  "notify":  { "on": "enter", "channels": ["webhook:1"] },  // 기본 꺼짐
  "owner":   "user:12",                 // 개인 기본. 팀 공유는 명시적
  "health":  "ok"                       // 시스템이 계산. ok | warn | broken
}
```

**사용자가 정하는 것은 조건 하나뿐이다.** 나머지는 전부 기본값 또는 선택.
이름·정렬·컬럼·알림을 건너뛰어도 쓸 만한 뷰가 나와야 한다.

### 2-3. 기본 표도 뷰다 `[변경]`

컬렉션의 메인 표 = **조건 없는 뷰 #0**. 특수 케이스로 두지 않는다.
이렇게 해야 네 출구가 전부 같은 코드(`packages/core/src/query`)를 탄다.

### 2-4. 네 출구

한 번 정의하면 동시에 네 곳에서 산다.

| 출구 | 의미 | 정렬·컬럼 | 페이지네이션 |
|---|---|---|---|
| 표 | 현재 매칭 (상태) | 뷰 설정 | 있음 |
| 웹훅·메일 | `enter` 이벤트 | 요약 문구 | 없음 (건당) |
| REST `?view=slug` | 현재 매칭 | 뷰 설정 (쿼리로 덮어쓰기 가능) | 있음 |
| MCP | 현재 매칭 | 뷰 설정 | 상위 N |

**MCP 는 뷰마다 도구 하나로 노출한다.** `search_items(view="deadline-soon")` 보다
`이번_달_마감_대학생()` 이 LLM 에게 훨씬 잘 먹힌다 — 도구 설명에 뷰 이름이 그대로 들어가므로.

### 2-5. 상태 vs 이벤트 — 전이 모델 `[신규]`

같은 조건이라도 표는 **상태**, 알림은 **이벤트**다. 알림 기준을 "새 항목"이 아니라 **전이**로 정의한다.

| 전이 | 이벤트 | v1 | 예 |
|---|---|---|---|
| 없음 → 맞음 | `enter` | ✅ | 새 공모전이 올라왔다 |
| 안 맞음 → 맞음 | `enter` | ✅ | 마감일이 채워져서 이제 걸린다 |
| 맞음 → 맞음 (값 변경) | `change` | ❌ G3 이후 | 마감이 연기됐다 |
| 맞음 → 안 맞음 | `exit` | ❌ | 조건에서 벗어났다 |
| 맞음 → 없음 | `gone` | ❌ | 공고가 내려갔다 |

**v1 은 `enter` 하나만.** 구현은 뷰별 매칭 id 집합을 저장해두고 run 마다 차집합.
`change` 이후는 항목 동일성 판정이 선행돼야 하므로 훨씬 비싸다.

### 2-6. 시간이 만드는 전이 `[신규]` — 놓치기 쉬운 요구사항

`마감 D-7 이내` 뷰는 **데이터가 안 바뀌어도 전이가 일어난다.** 어제 D-8 이던 것이 오늘 D-7 이 된다.
그리고 이것이 사용자가 가장 원하는 알림이다.

따라서:

1. **뷰 평가는 수집과 별개로 매일 돈다.** 소스가 조용해도 시간은 간다 → 스케줄러에 별도 잡
2. **조건 값은 반드시 상대 표현으로 저장한다.** `this_month` / `d7` 이지 `2026-08-31` 이 아니다.
   절대값으로 저장하면 뷰가 한 달 뒤 죽는다
3. `상시`(마감 없음) 항목이 마감 관련 뷰에 어떻게 취급되는지 명시 — **제외를 기본**으로 권장

정규화 파서에 이미 있는 `D-7` · `상시` 처리와 맞물린다.

### 2-7. 술어(op) 닫힌 집합 `[신규]`

변환 연산자를 zod 닫힌 집합으로 두고 목록 밖 `op` 를 거부하는 기존 규율을 **뷰 술어에도 동일 적용**한다.

| 필드 타입 | 허용 술어 |
|---|---|
| `date` | `within`(this_month/this_week) · `before` · `after` · `d_within` · `is_null` |
| `number` / `currency` | `gte` · `lte` · `between` · `is_null` |
| `enum` | `in` · `not_in` |
| `text` | `contains` · `not_contains` |
| `bool` | `is` |

**자유 표현식·SQL 조각은 열지 않는다.** 한 번 열면 네 출구 전부에서 안전성을 보장해야 하고
보장선 B2 점검에도 걸린다.

### 2-8. 뷰 건강 상태 `[신규]`

스키마가 바뀌면 뷰가 깨진다. **조용히 무시하면 안 된다** — 조건 하나를 빼고 결과를 주면
사용자는 걸러진 줄 알고 잘못된 목록을 본다.

| 상태 | 뜻 | 행동 |
|---|---|---|
| `ok` | 모든 참조 필드 살아있음 | 정상 |
| `warn` | 일부 소스에 그 필드 없음 | 동작하되 **"3개 소스 중 2개만 이 조건 적용됨"** 표시 |
| `broken` | 참조 필드 사라짐 | **알림 중단**, 작업실에서 교정 유도 |

`warn` 이 실제로 가장 자주 발생한다(소스마다 필드 커버리지가 다르므로).
이 표시 자체가 **누락 문제에 대한 답**이기도 하다 — 원문 대조는 "있는 값이 맞나"를 보장하지
"빠진 게 없나"를 보장하지 않는다.

### 2-9. 여러 개 `[신규]`

**컬렉션은 넓게, 뷰는 좁게.** 이것을 사용자 안내 원칙으로 삼는다.

컬렉션은 비싸고(소스 탐색 + 스키마 정렬) 뷰는 싸다(조건 하나).
뷰가 없으면 사용자는 "디자인 공모전"과 "개발 공모전" 컬렉션을 따로 만든다 — 소스가 겹치는데도.
뷰가 있으면 "공모전" 컬렉션 하나에 소스를 넉넉히 넣고 뷰로 갈라 쓴다.
소스가 늘수록 커버리지가 좋아지고 뷰가 늘수록 소음이 준다. 서로 싸우지 않는다.

부수 요구사항:

- **알림 중복 제거는 채널 단위** — 뷰 단위 발송이면 한 항목이 3개 뷰에 걸릴 때 3번 나간다.
  채널마다 모아 1번 보내고 "3개 뷰에 걸림" 표시. **이 결정을 나중에 뒤집기 번거로우므로 지금 확정**
- 메일은 하루 1회 묶음, 웹훅은 건별이되 같은 항목은 채널당 1회
- **뷰 복제** — 구현 거의 공짜. 실제 사용 패턴과 잘 맞음("D-7"에서 "D-3" 만들기)
- **고정/일반 구분** + **뷰별 건수 표시** — `이번 달 마감 (12)`. 0건은 흐리게.
  0건이 "해당 없음"인지 "고장"인지 구분되어야 하므로 2-8 과 연결
- **컬렉션당 20개 제한 권장** — 성능이 아니라 신호. 그 이상은 컬렉션이 너무 넓다는 뜻
- **이름 자동 제안 필수** — 뷰가 많아지면 이름이 유일한 식별 수단.
  조건 수정 시 **이름도 갱신할지 물어본다**(조건은 바꿨는데 이름이 옛 조건인 뷰가 가장 헷갈림)

### 2-10. 생성 흐름 `[신규]`

뷰 편집은 폼이 아니라 **표 위에서** 한다.

1. 표에서 필터를 걸어본다
2. **"이 조건 저장"** → 이름 자동 제안
3. (선택) 정렬·컬럼 조정
4. (선택) 알림 켜기

결과를 보면서 정의하므로 빈 뷰를 만들 일이 없다. **3·4 는 건너뛸 수 있어야 한다.**

## 3. 작업실 탭 — 구독 탭 개편 `[변경]`

### 3-1. 조직 원리

> **보기 탭 = 지금 상태. 작업실 = 내가 정해둔 것들이 사는 곳.**

일회성 행동은 들어가지 않는다. **내가 한 번 정하면 나 없이도 계속 작동하는 것**만 들어간다.
이 기준이 없으면 작업실은 "어디에도 안 맞는 것들의 서랍"이 된다.

### 3-2. 구성

| 구획 | 내용 | 시점 |
|---|---|---|
| **저장된 뷰** | 뷰 카드 목록 (조건 · 건수 · 최근 enter · 출구 · 건강) | **v1 핵심** |
| **소스 정비** | 소스별 유입 건수, 침묵 감지, 추가·제거 | v1 |
| **배달 채널** | 웹훅 URL · 메일 · MCP 토큰 (기존 구독 탭에서 승계) | v1 (이미 있음) |
| **스키마 편집** | `_raw` 필드 승격, 컬럼명 변경, 컬럼 접기 | G2 이후 |
| **매핑 교정** | 원문 대조에서 발견한 오류를 어댑터 스펙에 반영 | G2 이후 |

뷰 카드 표시 예:

```
이번 달 마감 · 대학생          [정상]
12건 · 최근 enter 2건 (어제)
표 · 웹훅#1 · API · MCP
```

### 3-3. 넣지 않을 것

- **추천 · 제안** — 정의권 침범 (4-4 참조)
- **일회성 내보내기(CSV 등)** — 그건 보기 탭의 버튼. 작업실 기준에 안 맞음
- **원시 필터 JSON 노출** — 보장선 B2 자동 점검에 직행.
  작업실은 화면 면적이 넓어 내부 명사가 새기 가장 쉬운 곳

### 3-4. 이름과 내용의 정합

"작업실"은 만드는 곳이라는 뜻이다. 저장된 뷰·스키마 편집은 맞지만
소스 정비·배달 채널은 설정에 가깝다. **작업실 안에서
"내가 만든 것"(뷰·스키마)과 "이 컬렉션의 상태"(소스·채널)를 시각적으로 분리**한다.

## 4. 능동성 `[변경]` + `[신규]`

### 4-1. 진단

능동 기능은 이미 있다(자가 치유 · 드리프트 검증 · 스케줄 수집 · 웹훅 발송).
다만 **전부 G3 의 인프라 항목으로 분류돼 사용자 눈에 보이는 행동이 아니다.**
수동적으로 느껴지는 원인은 기능 부족이 아니라 **관찰한 걸 말해주는 입이 없는 것**이다.

### 4-2. 세 층

| 층 | 내용 | 현재 |
|---|---|---|
| 1층 수집 능동 | 스케줄 수집 · 자가 치유 | 있음, **안 보임** |
| 2층 감시 능동 | 마감 임박 · 신규 등장 알림 | 반쯤 (채널만 있고 종류 미정) |
| 3층 **컬렉션 건강 능동** | 소스 침묵 · 필드 승격 제안 · 값 변경 | **없음 ← 여기가 비어 있다** |

3층이 가장 강하다. **사용자가 알 수 없는 걸 시스템만 알 수 있기 때문**이다.
사이트 3곳을 직접 보던 사람은 한 곳이 조용히 죽은 걸 몇 주 뒤에나 알아챈다.

### 4-3. 추가할 것

**소스 침묵 감지 `[신규]` — 최우선.**
Run 별 신규 건수 추이만 보면 되므로 비용이 거의 없는데(Run 테이블 이미 존재) 3층에 속한다.

> "씽굿이 3주째 새 항목이 없습니다. 사이트가 바뀌었거나 시즌이 끝난 것 같습니다."

**상단 상태 줄 `[신규]` — 기능보다 먼저.**
컬렉션 상단 한 줄이면 "살아있다"는 인상이 만들어진다. 지금 있는 것만으로 대부분 채워진다.

```
3시간 전 확인 · 새 항목 2건 · D-3 이내 3건 · ⚠ 씽굿 3주째 조용함
```

비용 순서:

| 항목 | 필요한 것 | 비용 | 시점 |
|---|---|---|---|
| 마감 임박 | `deadline` 쿼리만 | 30분 | v1 |
| 신규 등장 | 본 적 있는 id 집합 | 2시간 | v1 |
| **소스 침묵 감지** | run 별 신규 건수 추이 | 2시간 | **v1** |
| 값 변경 (마감 연기) | 항목 동일성 판정 | 반나절~ | G3 이후 |
| 사라짐 감지 | 위 + 페이지네이션 밀림 구분 | 하루 | G3 이후 |

### 4-4. 금지 — 추천·제안 `[정체성]`

"이런 사이트도 추가해보세요", "이 공모전이 맞을 것 같아요" 류를 **넣지 않는다.**

- 매 호출에 LLM 이 개입해 결정성이 깨진다 (LLM 은 컴파일 경로에만 — 기존 원칙)
- **정의권을 침범한다.** 카테고리를 내가 정하는 게 강점인데 시스템이 대신 정하면 또 하나의 추천 서비스

올바른 능동성의 형태:

> **정의는 사용자가, 관찰은 시스템이.**

판단은 여전히 사용자 것이고 관찰만 시스템이 한다. 이 선을 지키면 능동성과 정의권이 충돌하지 않는다.

## 5. 컬렉션 생성 입구 `[변경]`

### 5-1. 문제

"URL 5개를 알고 있어야 시작 가능"이면 정의권은 이미 URL 을 아는 사람만의 것이다. 강점이 절반 죽는다.

### 5-2. 분해

> **"이번 달 마감인"** + **"디자인 공모전"**
> └ 필터 (스키마 위의 쿼리) └ 소스 (어느 사이트를 볼 것인가)

| | 비용 | 시점 |
|---|---|---|
| 앞부분 = 필터 자연어 | **거의 공짜.** `normalize/date` + `query` 에 얹으면 됨. 반나절 | **v1** |
| 뒷부분 = 소스 발견 | 검색 필요 + 결과 대부분이 목록형이 아님(블로그 정리글·개별 상세·기존 애그리게이터) | **G2 이후** |

### 5-3. URL 은 입력이 아니라 계약이다 `[정체성]`

사용자가 URL 을 넣으면 **커버리지를 본인이 안다** — "내가 넣은 3곳이 이 표의 전부다."
시스템이 소스를 고르면 이게 사라진다. 12건이 전부인지 중요한 사이트가 빠졌는지 알 수 없다.

**그리고 이건 원문 대조로 막을 수 없다.** 원문 대조는 "있는 값이 맞나"를 보장하지
"빠진 게 없나"를 보장하지 않는다. 누락은 화면에 안 보이는 게 문제고 신뢰가 깨지는 방식도 더 나쁘다.

### 5-4. 결론 — 자연어는 입구, URL 은 계약

```
"이번 달 마감인 디자인 공모전"
   ↓  후보 제시 (검색)
   ☑ 디자인정글 공모전       목록형 · 주 3회 갱신 추정
   ☑ 씽굿                    목록형 · 매일 갱신 추정
   ☐ ○○블로그 공모전 정리    단발 글 — 권장 안 함
   ＋ 직접 추가
   ↓  사용자 확정
컬렉션 생성 (소스 = 확정된 URL 들)
필터: deadline ≤ 이번 달 말
```

저장 단위는 그대로 URL. 자연어는 **한 번 쓰고 버리는 입구**지 컬렉션의 정체성이 아니다.
G0 고정 다섯 가지를 건드리지 않는다.

**자연어 해석 결과는 항상 화면에 보여준다** — "이번 달 마감"이 `deadline within this_month` 로
해석됐다는 게 보여야 신뢰가 생긴다.

### 5-5. 빈 화면 금지 `[신규]`

정의권이 강점이면 "정의하는 경험"이 매끄러워야 한다. 빈 입력창을 그대로 두지 않는다.
**예시 컬렉션 3~4개**(디자인 공모전 · 대학 장학 · 지원사업)를 첫 화면에 두고 열어보게 한다.
온보딩 편의가 아니라 **강점을 실제로 전달하는 장치**다. 빈 화면 문제의 90% 가 이걸로 해결된다.

## 6. 스키마 진화 정책 `[신규]` — G2 전에 확정 필요

### 6-1. 문제

여섯 번째 소스에만 `주최기관` 필드가 있으면?

| 선택 | 대가 |
|---|---|
| 버린다 | 정보 손실 (`_raw` 에는 남음) |
| 통합 스키마에 추가 | **기존 5개 소스 전부 null.** 표에 빈 컬럼 |
| 매번 물어본다 | 소스 추가할 때마다 질문 공세 |

### 6-2. 결정

**기본은 버리되 언제든 승격 가능.**

1. 새 필드는 일단 `_raw` 에만 두고 표에 안 띄운다
2. 대신 **능동 알림으로 흘린다** — "디자인정글에만 있는 필드 2개가 있습니다 — 추가할까요?"
3. 승격 버튼은 작업실 > 스키마 편집에

질문을 소스 추가 시점이 아니라 나중으로 미루므로 온보딩이 안 막히고 정의권도 유지된다.

### 6-3. `schema_version` 의 의미 확정 `[결정필요]`

응답에 `schema_version` 이 이미 들어 있다. 아래를 명시해야 한다.

- 스키마가 바뀌면 기존 API 소비자의 코드가 깨지는가
- 웹훅 구독자에게 알려야 하는가
- 뷰가 참조하던 필드가 사라졌을 때 → 2-8 의 `broken`

## 7. 원문 대조 이후 — 교정 경로 `[신규]`

원문 대조는 사용자가 **틀린 걸 발견하게** 해준다. 그다음이 비어 있다.
고칠 수 없으면 원문 대조는 "이 도구는 틀린다"는 증거로만 작동한다. **신뢰 장치가 불신 장치가 된다.**

| 방식 | 평가 |
|---|---|
| 그 항목만 수정 | 쉽지만 다음 run 에 또 틀림 |
| **어댑터 스펙을 수정** | ✅ 맞는 방향. 매핑 자체를 교정 |

README 의 "사람이 판단할 것 — *정규화가 맞는가*" 와 사상적으로 일관된다.
그리고 **"LLM 이 만들고 사람이 승인한다"** 는 구조는 완전 자동화보다 오히려 신뢰를 준다.

시점: G2 이후 (작업실 > 매핑 교정).

## 8. 창작마당 `[신규]` — 공개 컬렉션

### 8-1. 모델은 복제

**구독이 아니라 복제.** 남의 컬렉션을 그대로 보는 게 아니라
**가져와서 소스를 빼고 더할 수 있어야** 정의권이 살아있다.

이미 slug 기반 공개 API 가 있으므로 구조는 대부분 되어 있다. 필요한 건 "이 컬렉션 복제하기".

### 8-2. 무엇을 푸는가

| 문제 | 어떻게 |
|---|---|
| 빈 화면 | 사용자들이 만든 컬렉션이 곧 예시가 된다 |
| 소스 발견 (5-2 뒷부분) | 남이 이미 찾아놨으면 검색이 필요 없다 |
| 정의권과의 충돌 | 없음 — 복제 후 수정 가능하므로 여전히 내 카테고리 |

### 8-3. 공유 단위가 다르다

parse.bot 류 마켓플레이스와 형태는 비슷하나 **공유 단위가 사이트가 아니라 컬렉션**이다.
"zillow API" 는 재료고, "이번 달 마감 디자인 공모전" 은 그 자체로 쓸 수 있는 완성품이다.

### 8-4. 뷰의 취급

**뷰만 따로 공유하지 않는다.** 받는 쪽 스키마와 안 맞는다.
컬렉션을 복제할 때 뷰가 딸려가는 것이 맞다.

시점: G4 이후.

## 9. 초대 링크 · 권한 `[신규]`

### 9-1. 창작마당과 다른 기능이다

| | 창작마당 | 초대 링크 |
|---|---|---|
| 모델 | **복제** — 가져가면 내 것 | **공유** — 같은 것을 함께 |
| 정의권 | 유지 | 나눠 가짐 |

묶어서 설계하면 나중에 갈라야 한다.

### 9-2. 3단계 권한 — 뷰어/편집자 2단계로는 부족

행동마다 영향 범위가 다르다.

| 행동 | 영향 |
|---|---|
| 뷰 만들기 | 나만 (또는 팀) |
| 소스 추가·삭제 | **팀 전체가 보는 데이터가 바뀜** |
| 스키마 편집 | **모든 뷰가 깨질 수 있음 + 외부 API 소비자까지** |
| 웹훅 URL · 토큰 | **자격증명** |

특히 스키마 편집은 문서 편집과 달리 **되돌리기가 안 되는 종류의 변경**이다.

| 역할 | 할 수 있는 것 |
|---|---|
| **뷰어** | 표 보기 · 자기 뷰 만들기 |
| **편집자** | + 소스 추가·삭제 · 매핑 교정 |
| **관리자** | + 스키마 편집 · 토큰 관리 · 초대 |

### 9-3. 자격증명 — 구글 독스에 없는 문제

- 뷰어에게는 **마스킹** (`https://hooks.slack.com/···abc`)
- **토큰 회전 기능 필수** — 사람이 나가면 갈아야 한다. 없으면 공유 기능이 반쪽
- **개인 채널(내 메일)과 팀 채널(팀 슬랙) 분리**

### 9-4. 뷰 소유권

**뷰는 기본 개인, 명시적으로 팀에 공유.**
팀원 다섯이 각자 뷰를 만드는데 다 섞이면 작업실을 못 쓴다.

### 9-5. 팀 시나리오는 실제로 좋다 — 다만

"소규모 개발팀이 API·MCP 를 함께 관리" 는 개인 도구보다 용도가 명확하다.
컬렉션이 팀의 공유 자산이 되고 한 명이 만들면 다섯이 쓴다.

**다만 이건 제품 성격을 바꾼다.** 보장선 B1~B7 의 비개발자 지향과 방향이 다르다 → 1-3 결정 필요.

시점: G4 이후.

## 10. 시간축 데이터 `[신규]` — 지금은 "버리지 않기"만

Run 이 돌 때마다 스냅샷이 쌓인다. 지금은 현재 상태 표시에만 쓰이지만 몇 달 뒤 다른 물건이 된다.

- "이 공모전은 작년 이맘때도 있었습니다" → 놓친 사람에게 내년 예고
- "이 사이트는 보통 화요일에 새 공고가 올라옵니다" → 언제 봐야 하는지
- "작년 이 시기 평균 12건, 올해 4건" → 이상 감지

특히 **주기성 감지** — 공모전·장학·지원사업은 대부분 연 단위로 반복되는데 아무도 데이터로 안 본다.
사람은 작년에 뭐가 있었는지 기억하지 못한다.

**지금 만들 게 아니라 버리지만 않으면 된다.** Run 이력과 항목 스냅샷을 삭제하지 않는다.
나중에 켤 수 있는 스위치를 공짜로 갖고 있는 셈.

## 11. probe · 타입 추론 `[변경]`

### 11-1. 4단계 순서 확인 및 보강

README 의 `인라인 JSON → 네트워크 관찰 → DOM → 브라우저` 순서가 맞다. 아래를 명시한다.

| 단계 | 구체 | 왜 우선인가 |
|---|---|---|
| 1. 인라인 상태 | `__NEXT_DATA__` · `__NUXT__` · `window.__INITIAL_STATE__` | 브라우저 없이 정적 요청만으로 통째 JSON. 정규식 한 줄 |
| 2. 네트워크 관찰 | 클릭 → 나가는 요청 캡처 | **타입이 이미 붙어 있다.** 아래 11-2 문제의 절반이 사라짐 |
| 3. DOM | `networkidle` 후 파싱 | 확실하지만 느리고 타입 추론 문제가 남음 |
| 4. 브라우저 유지 | — | 최후 |

**URL 을 조립하지 말고 클릭 후 관찰한다.** 전자정부 표준프레임워크의
`javascript:fn_egov_link_page(2)` 패턴은 쿼리스트링 실험으로는 잡히지 않는다.

### 11-2. 요청 재현 검증 단계 추가 `[신규]`

캡처한 요청을 런타임에 브라우저 없이 재현하는 것이 전제인데, 항상 되지는 않는다
(페이지 로드 시 받은 쿠키·CSRF 토큰 필요, 토큰 수명 짧음 → 나중에 401).

**빌드 타임에 캡처 직후 한 번 재현해보고, 실패하면 그 소스를 DOM 폴백으로 내린다.**
30분이면 붙고, 나중에 조용히 깨지는 것을 막는다.

### 11-3. 실측된 타입 추론 실패 3종 `[신규]`

실제 사이트(KAIST 소프트웨어대학원 공지 · 서울이스케이프룸)로 값 분포 기반 추론기를 돌린 결과.

**성공** — `2026.01.21` → date · 제목 → text · `65분` → duration · `3~5` → range · `10:00` → time.
**필드명을 전혀 보지 않고 값만으로 맞췄다.** 한국어 필드명 사전 없이 `소요시간` 과 `참여인원` 이 구분됐다.

**실패 — 여기가 실제 난이도가 있는 자리다.**

| 실패 | 원인 | 필요한 것 |
|---|---|---|
| `번호` 컬럼 판정 실패 | 상단 고정 공지 때문에 `["공지사항","45","44"...]`. **한국 게시판에 거의 항상 있다** | 이상치 제거 후 다수 패턴으로 판정 |
| `조회` 를 id 로 오판 | 값이 전부 유일하다는 이유. 고유값 비율만으로는 id 와 카운트를 구분 못 함 | 분포 형태 · 단조성 등 추가 신호 |
| 모든 필드가 `enum(1)` | 한 페이지에 한 테마만 노출됨 | 여러 페이지 훑기 또는 select 옵션 읽기 |

셋 다 LLM 에 던지면 대충 풀리지만 **직접 풀면 "기능이면서 어려운" 자리**다.

### 11-4. Day 0 정찰 `[신규]`

본격 착수 전 사이트당 세 가지만 눈으로 확인(코드 없이 F12):

1. 페이지 소스에 `__NEXT_DATA__` 류가 있는가 → 있으면 즉시 통과
2. Network > Fetch/XHR 에 목록 JSON 이 잡히는가 → 잡히면 통과
3. 둘 다 없으면 DOM 폴백 대상 → 몇 개까지 감당할지 판단

**실측 근거**: 방탈출 도메인은 후보 5곳 중 1곳만 서버 렌더링이었다(나머지는 정적 요청에 본문이 비어 있음).
정찰 없이 착수했으면 이틀을 잃었을 것.

### 11-5. 소스별 필드 결손 `[신규]`

서울이스케이프룸에는 **가격 필드가 아예 없었다.**
통합 스키마를 만들면 소스별로 없는 필드가 생기며 다음이 필요하다.

- `null` 처리
- **"이 소스는 이 필드 없음" 표시** — 2-8 의 `warn` 과 직결

## 12. 항목별 개인 표시 `[신규]` — G4 이후

관심 있음 / 숨김 / 지원 완료.

공모전·공고 컬렉션에서 효과가 크다. "이미 지원한 것"과 "관심 없어 넘긴 것"이 매번 다시 뜨면
목록이 계속 소음이 된다. 그리고 도구의 성격이 **보는 곳 → 관리하는 곳**으로 바뀐다.

대가: 테이블 추가, 소스 데이터와 사용자 데이터가 섞이기 시작, 항목 id 가 바뀌면 표시가 날아감.

## 13. 데이터 모델 영향 요약

### 13-1. G0 고정 전에 판단할 것 `[결정필요]`

| 항목 | 이유 |
|---|---|
| **소유자를 user 직접 참조 대신 한 단계 띄우기** | 9절 팀 기능. 나중에 마이그레이션이 훨씬 쉬워진다 |
| **뷰 테이블에 owner 필드** | 지금은 전부 생성자지만 나중에 개인/팀이 갈린다 (9-4) |
| **Run 을 컬렉션이 아니라 소스 단위로** | 창작마당에서 같은 URL 이 N개 컬렉션에 복제될 때. *부하 이슈는 이번 논의에서 제외 요청됐으므로 선택 사항이나, 스키마 타이밍상 지금 판단하는 편이 싸다* |

### 13-2. 신규 테이블 / 컬럼

- **`views`** — slug · name · where · sort · columns · notify · owner · health · collection_id
- **`view_matches`** — 뷰별 매칭 id 집합 (`enter` 차집합 계산용)
- **`notification_dedupe`** — 채널 단위 중복 제거 (2-9)
- `sources` 에 침묵 감지용 최근 신규 건수 추이 (또는 Run 집계로 대체 가능)
- 컬렉션에 `visibility`(private / unlisted / public) — 8절
- 멤버십 테이블 (role: viewer / editor / admin) — 9절

### 13-3. 유지

- Run 이력 · 항목 스냅샷 **삭제하지 않는다** (10절)
- `raw_json` / `provenance_json` 은 이미 시드에 있음 — 7절과 11-5 에서 계속 쓴다

## 15. 보장선(guardrails) 영향

- **B2 점검 범위에 작업실 화면 추가** — 화면 면적이 넓어 내부 명사가 가장 새기 쉬운 곳.
  `where` · `op` · `slug` · `adapter` · `drift` 등이 사용자 화면에 노출되지 않는지
- **뷰 상태 문구가 사람 말인지** — "warn" 이 아니라 "3개 소스 중 2개만 이 조건이 적용됩니다"
- **자연어 해석 결과 표시**(5-4)가 내부 표현을 그대로 뱉지 않는지 —
  `deadline within this_month` 를 그대로 보여주면 B2 위반. "마감이 이번 달 안" 으로

## 16. 논의했으나 채택하지 않은 것

기록해 두어 나중에 다시 꺼내지 않도록.

| | 왜 |
|---|---|
| "자유도"를 강점으로 내세우기 | 1-1. 공허하고, 빈 화면 문제를 키운다 |
| 추천 · 제안 기능 | 4-4. 정의권 침범 + 결정성 파괴 |

| 뷰만 따로 공유 | 8-4. 받는 쪽 스키마와 안 맞음 |
| 컬렉션을 넘나드는 뷰 | 스키마가 다르면 필드 참조가 성립 안 함. 별도 문제 |

| 뷰어/편집자 2단계 권한 | 9-2. 스키마 편집의 파급이 너무 다르다 |
| 자유 표현식 · SQL 조각 술어 | 2-7. 네 출구 전부에서 안전성 보장 불가 |
