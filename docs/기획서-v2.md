## 0. 이 문서를 고치는 방법

이 문서는 두 부분의 수명이 다르다. 고칠 때 이 구분을 지켜야 문서가 망가지지 않는다.

| 파트 | 내용 | 수명 |
|---|---|---|
| **Part I — 제품** | 1~6장. 무엇을 왜 만드는가 | **고정.** 아이디어는 바뀌지 않는다 |
| **Part II — 기술** | 7~12장. 어떻게 만드는가 | **교체 가능.** 조건이 추가되면 여기만 고친다 |
| **Part III — 실행** | 13~16장. 5일을 어떻게 굴리는가 | 관문 판정 결과에 따라 갱신 |

기술 결정은 전부 **부록 B의 ADR 로그**에 번호를 달아 놓았다. 기술 조건이 추가되거나 바뀌면:

1. 부록 B에서 해당 ADR을 찾는다
2. "이걸 다시 보게 만드는 조건" 열에 그 변경이 해당하는지 확인한다
3. 해당하면 ADR을 갱신하고, "영향받는 곳" 열에 적힌 장절만 고친다
4. Part I은 건드리지 않는다

Part I을 고쳐야 한다는 결론이 나오면, 그건 기술 변경이 아니라 제품 변경이다. 그때는 문서 버전을 v3로 올린다.

# Part I — 제품

> 이 파트는 고정이다. 기술 조건이 바뀌어도 여기는 그대로다.

## 1. 한 줄 정의와 문제의식

> **같은 종류의 웹사이트 여러 곳을, 내가 정한 스키마 하나로 계속 받아보는 도구.**
>
> "계속"이 핵심이다. 한 번 뽑고 끝나는 추출 도구가 아니라, 한번 만들면 살아서 갱신되는 컬렉션이다.

다나와는 남이 정해준 카테고리만 비교할 수 있다. 노트북, 냉장고, 그래픽카드. 그런데 내가 궁금한 건 이번 달 마감인 디자인 공모전이거나 우리 동네 클라이밍장 요금인데, 그런 다나와는 세상에 없다.

그러면 내가 만든다. URL 몇 개를 지정하면 그 주제의 다나와가 생기고, 그것을 표로도, 읽기로도, API로도, MCP로도 쓴다.

### 시장에 뚫려 있는 구멍

| 있는 것 | 할 수 있는 것 | 못 하는 것 |
|---|---|---|
| **다나와 · 에누리** | 정해진 카테고리 안에서 여러 판매처를 하나의 규격으로 비교 | 카테고리가 고정. 내가 원하는 주제의 비교표는 만들 수 없음 |
| **Firecrawl · Kadoa · AgentQL · Apify** | 사이트 **하나**를 구조화된 데이터로 추출 | 여러 사이트를 하나의 스키마로 묶는 계층이 없음. 각자 파이프라인을 직접 짬 |
| **RapidAPI 류 디렉터리** | 이미 존재하는 API를 목록으로 제공 | API가 없는 사이트에 대해서는 아무것도 못 함 |

즉 **"내가 카테고리를 정하고, 거기에 사이트를 여러 개 붙여서, 하나의 규격으로 계속 받아본다"** 는 조합이 비어 있다. 추출 기술은 이미 성숙했으므로 이 제품의 난이도는 추출이 아니라 **통합**과 **유지**에 있다.

### 전제

LLM 덕분에 "한 페이지에서 구조화 데이터 뽑기"는 더 이상 어려운 문제가 아니다. 남은 어려운 문제는 세 가지다.

1. **정규화** — 서로 다른 사이트의 값을 같은 규격으로 맞추는 일
2. **드리프트** — 사이트가 바뀌어도 안 깨지게 하는 일
3. **UX** — 이걸 개발자가 아닌 사람도 만들 수 있게 하는 일

**3번이 이 프로젝트의 핵심 제약이다.** 1번과 2번은 어렵지만 정직한 엔지니어링 문제이고, 3번은 잘못 설계하면 아무리 1·2번을 잘 풀어도 제품이 없어지는 문제다. 그래서 4장에 별도의 보장선을 두었다.

## 2. 컨셉 — 만들기와 쓰기

> URL → API는 만드는 방법이고, 다나와는 만들어진 물건이다

제품은 두 동작으로 이루어진다. **URL 몇 개로 컬렉션을 만드는 것**, 그리고 **그 컬렉션을 여러 표면으로 소비하는 것**. 이 둘은 대립하는 게 아니라 앞뒤다. 기존 크롤링 도구는 앞만 있고, 다나와는 뒤만 있다.

```
SOURCES                    COLLECTION · 하나의 스키마          SURFACES
─────────────              ─────────────────────────         ─────────────
k-startup.go.kr            title · organization              표 · 즐겨찾기
bizinfo.go.kr        →     deadline · category         →     읽기 피드
thinkcontest.com           amount                            REST API
+ 아무 목록 페이지          정규화 · 검증 · 자가 치유          MCP 서버
```

다나와와의 결정적 차이가 오른쪽에 있다. 다나와는 용도가 하나다. 비교하고 최저가를 누르면 끝난다. 이 제품은 **한 번 만들어 여러 방식으로 소비된다.** 만드는 비용은 한 번만 치르고, 쓰임새는 계속 늘어난다. 이것이 "커스텀 다나와"라는 표현이 가리키는 실체다.

### 설계 원칙

표도 API도 **본체가 아니다.** 둘 다 표면이고, 본체는 그 밑의 컬렉션 하나다. 따라서 어느 한쪽을 주인공으로 세운 화면은 틀린 화면이다. "만들기" 다음에 "어떻게 쓸까"가 나란히 놓이는 구조여야 한다.

## 3. 네 개의 표면

> 같은 컬렉션이 네 가지 얼굴로 나간다

### 표 · 즐겨찾기 — 다시 와서 보는 사람
여러 출처가 하나의 표에 섞여 정렬·필터되는 화면. 내가 만든 컬렉션들이 목록으로 쌓이고, 그 안에서 관심 항목을 따로 담아둘 수 있다. 가장 다나와에 가까운 얼굴.

### 읽기 피드 — 훑는 사람
표가 아니라 흐름으로 소비하는 화면. 새로 올라온 것만, 마감이 임박한 것만. 여기에 **구독**이 붙는다 — 정해진 시각에 새 항목만 웹훅이나 메일로. 리텐션의 핵심 장치.

### REST API — 코드가 쓰는 것
`GET /v1/{collection}` 하나. 표에서 건 필터와 정렬이 그대로 쿼리 파라미터가 된다. 스키마를 바꾸면 응답 스펙이 바뀌므로 버전이 발행되고 breaking change가 경고된다.

### MCP 서버 — AI 에이전트가 쓰는 것
컬렉션이 곧 도구가 된다. 사용자가 자기 AI에게 "내 공모전 컬렉션에서 이번 주 마감 뭐 있어?"라고 물을 수 있다. 개발을 못 해도 자기 데이터를 대화로 쓰게 되는, API의 대중화 버전.

---

네 표면 중 **MCP가 가장 차별적이다.** 경쟁 제품 중 이 축을 가진 곳을 아직 찾지 못했고, 이것이 붙는 순간 "개발자만 쓰는 도구"라는 천장이 사라진다. 다만 구현 난도는 낮다 — 이미 스키마와 엔드포인트가 있으므로 MCP 래퍼는 얇은 계층이다. **가성비가 가장 좋은 차별점.**

**v2에서 추가하는 판단:** 비개발자에게 MCP는 "API보다 쉬운 API"가 아니라 **"API를 몰라도 되는 경로"** 다. 따라서 MCP 연결 UX는 주소 한 줄을 복사해 커넥터에 붙여넣는 것으로 끝나야 한다. 설정 파일 편집을 요구하는 순간 이 표면의 존재 이유가 사라진다. (12장 MCP 계약 참조)

## 4. 사용자

> 누가 쓰는가, 그리고 누가 쓰지 않는가

| 페르소나 | 상황과 필요 | 주 표면 |
|---|---|---|
| **지훈 · 27** <br> 백엔드 3년차, 사이드프로젝트 | 아이디어는 하루 만에 나왔는데 사이트 네 곳 크롤러 짜다가 주말 두 번 태우고 접었다. 프로젝트의 재미없는 80%를 지워주는 게 가치. | API · MCP |
| **수영 · 34** <br> 뉴스레터 운영, 구독자 4천 | 매주 월요일 오전을 통으로 써서 사이트 열몇 곳을 순회하고 복붙한다. 개발은 못 하지만 그 반나절이 곧 매출이다. | 읽기 · 구독 |
| **민재 · 31** <br> B2B 영업기획 | 경쟁사 가격, 입찰 공고, 채용 사이트를 계속 봐야 한다. 지금은 인턴이 손으로 옮기거나 아예 안 본다. | 표 · 즐겨찾기 |

### 민재를 초기에 받으면 안 되는 이유

팀 공유, 권한, 엑셀 내보내기, 감사 로그, 이어서 SSO와 계약서가 따라온다. 제품이 순식간에 엔터프라이즈 SaaS로 끌려가고 UX가 아니라 영업을 하게 된다. 프로젝트성으로 만드는 이번 5일에서는 특히 순서상 마지막이다.

### 명시적 비사용자

대기업 데이터팀(이미 인하우스 파이프라인이 있음), 수백만 페이지급 대규모 크롤링(본질이 프록시·차단 우회라 강점이 다른 곳에 있음), 로그인 뒤 데이터(계정 관리와 세션 유지가 별도의 제품이 됨).

### 진입 순서와 그 근거

**지훈으로 시작해 수영으로 확장한다.** 근거는 감이 아니라 구조다. 지훈은 컬렉션을 **만드는** 사람이고 수영은 **소비하는** 사람이다. 지훈이 "채용 공고 통합" 스키마를 잘 만들어두면 수영은 그것을 복제해 바로 쓴다. 한쪽이 다른 쪽의 공급이 되는 양면 구조가 한 제품 안에 성립하고, 이것이 후반의 스키마 레지스트리에 저절로 씨앗을 심는다.

### 사용 동기와 리텐션

| 동기 | 내용 | 리텐션 |
|---|---|---|
| **만들기** | 없는 데이터를 만들어 무언가를 짓는다 | 초기에 몰리고 이후 조용해짐 |
| **지켜보기** | 여러 곳을 계속 감시한다 | **매주 돌아옴 — 반복이 내장** |
| **모으기** | 일회성으로 데이터셋을 뽑는다 | 한 번 쓰고 떠남 |

따라서 제품의 기본값은 **일회성 추출이 아니라 계속 지켜보는 컬렉션**이어야 한다. 이 한 줄이 뒤에 나오는 기능 우선순위 전체를 결정한다.

### 4-1. 비개발자 보장선 (v2 신설 · 최상위 제약)

"개발자도 쓸 수 있지만 비개발자도 손쉽게"가 이 기획의 핵심이다. 그런데 이건 구호로는 지켜지지 않는다. 아래 일곱 줄은 **검수 가능한 제약**이고, 어느 하나라도 깨지면 그 기능은 미완성으로 판정한다. 관문 판정(13장)에서도 이 표를 그대로 쓴다.

| # | 보장선 | 위반 판정 방법 |
|---|---|---|
| **B1** | 컬렉션을 만드는 전 과정에서 사용자가 입력하는 것은 **URL**과 (필요 시) **값 붙여넣기**뿐이다 | 셀렉터·XPath·정규식·JSONPath·타입 코드를 입력받는 화면이 하나라도 존재하면 위반 |
| **B2** | 사용자가 배우는 명사는 **"컬렉션" 하나**다 | UI 문자열에 어댑터·런·스펙·드리프트·파서 같은 내부 명사가 등장하면 위반 |
| **B3** | 빈 스키마 에디터를 주지 않는다. 언제나 **이미 채워진 표**를 주고 사용자는 편집만 한다 | 첫 화면에 "필드를 추가하세요"라는 빈 상태가 나오면 위반 |
| **B4** | 실패는 빨간 에러가 아니라 **상태 문구**다 | "이 사이트 구조가 바뀐 것 같아요, 다시 맞추는 중입니다" 대신 스택 트레이스나 HTTP 코드가 노출되면 위반 |
| **B5** | API URL과 MCP 주소는 기본으로 **접혀 있고**, 펼치면 언제든 보인다 | 첫 진입 화면에 엔드포인트 문자열이 강제 노출되면 위반 (숨겨서 못 찾게 해도 위반) |
| **B6** | 표를 만들고 결과를 보기까지 **터미널·새 탭·외부 도구가 필요 없다** | curl 실행이나 파일 다운로드를 요구하는 단계가 있으면 위반 |
| **B7** | MCP 연결은 **주소 한 줄 복사 → 커넥터에 붙여넣기**로 끝난다 | 설정 JSON 편집이나 로컬 설치를 요구하면 위반 |

**개발자를 위한 것은 빼는 게 아니라 접는다.** B5가 그 원칙을 대표한다. 지훈이 원하는 건 다 있되, 수영의 첫 화면에는 안 나온다. 두 사람을 위해 화면을 두 벌 만드는 게 아니라, 하나의 화면에서 접힘 상태만 다르다.

## 5. 핵심 기능

> 컬렉션의 생애주기가 곧 기능 목록이다

### ① 스키마 추론 — 첫 표를 대신 만들어준다
URL 하나를 받아 목록 구조를 감지하고 필드를 추측해 **이미 채워진 표**를 내놓는다. 사용자에게 빈 스키마 에디터를 주지 않기 위해 존재한다. 사용자가 하는 일은 생성이 아니라 편집이고, 그 편집은 이름 바꾸기와 필요 없는 것 지우기 두 가지뿐이다. 필드 추가는 셀렉터 입력이 아니라 **값의 예시를 붙여넣는 방식**으로 받는다. → 보장선 B1, B3

### ② 소스 접합 — 제품의 정체성
기존 스키마에 두 번째, 세 번째 사이트를 붙이는 기능. **이 제품이 다른 제품과 갈라지는 유일한 지점.** 핵심은 스키마가 이미 있다는 사실을 활용하는 것이다. 처음부터 묻지 않고 기존 필드를 새 사이트에서 자동으로 찾아본 뒤 **못 찾은 것만** 예시를 요청한다. 여기서 사용자가 하는 일이 많아지면 두 번째 소스를 붙이지 않고, 그러면 이 제품을 쓸 이유가 사라진다.

### ③ 타입 정규화 — 통합이 진짜가 되는 지점
컬럼에 타입을 붙인다. 날짜, 금액, 텍스트, 링크, 분류. 타입이 없으면 `2026.08.14 18:00`과 `~2026-08-21`과 `08/14` 마감이 한 컬럼에 뒤섞여 "스키마가 하나"라는 말이 거짓이 된다. 타입이 있으면 네 가지가 한꺼번에 풀린다.

- 소스가 달라도 값의 형식이 같아진다 (정규화)
- 정렬과 필터가 가능해진다
- API 응답이 예측 가능해진다
- **값이 타입에 안 맞으면 그 자체가 고장 신호가 된다** — ④가 여기에 얹힌다

분류 타입은 한 겹 더 필요하다. A사이트의 "기술개발"과 B사이트의 "R&D"를 같은 값으로 묶는 매핑을 사용자가 한 번 알려주면 기억한다.

### ④ 자가 치유 — 지켜보기를 가능하게 하는 것
매 수집마다 결과를 스키마로 검증한다. null 비율이 튀거나 타입이 안 맞으면 드리프트로 판정하고, 해당 소스만 격리한 뒤 어댑터를 재컴파일한다. 새 어댑터가 검증을 통과하면 자동 승격, 실패하면 사람 호출. 어댑터는 버전으로 남아 롤백 가능하다.

이것은 부가 기능이 아니라 **구독의 이유**다. 지켜보기가 주 용도인 제품에서는 안 깨지는 것 자체가 제품이다. 그러므로 조용히 고치지 말고 **"이번 달 자동 복구 7회"** 처럼 로그로 쌓아 보여준다.

### ⑤ 네 개의 표면 — 03장 참조
표·즐겨찾기, 읽기·구독, REST API, MCP 서버. 출력 옵션이 아니라 제품의 절반이다.

### 관통하는 신뢰 계층

다음 둘은 화면이 아니라 성질이므로 따로 센다.

- **커버리지** — 부분 성공을 정상 상태로 보여주는 것. 소스별 상태가 API 응답에도 있고 화면 상단에도 있다.
- **원문 대조** — 모든 값이 자기가 어디서 왔는지 증명할 수 있는 것.

이 둘이 빠지면 나머지가 다 있어도 결과를 믿지 못해 쓰지 않는다. 늦게 넣지 말고 처음부터 넣는다.

### 냉정한 우선순위

①③⑤는 경쟁 제품도 이미 하거나 마음먹으면 금방 한다. **고유한 것은 ②와 ④뿐이다.** 리소스가 부족하면 ①③⑤는 조잡해도 되지만 ②와 ④는 조잡하면 안 된다.

**v2 보강:** 여기에 **비개발자 보장선(4-1)** 이 같은 급으로 하나 더 들어간다. ②와 ④가 아무리 잘 돌아도 B1~B7이 깨지면 이 제품은 Firecrawl의 열등한 사본이 된다. 즉 사수해야 할 것은 세 개다 — **②소스 접합, ④자가 치유, B1~B7 보장선.**

## 6. 하지 않을 것

> 범위 방어는 기능 목록만큼 중요하다

| 제외 항목 | 이유와 조건 |
|---|---|
| **자동 중복 병합** | "A사이트의 이 항목과 B사이트의 저 항목이 같다"는 판정은 엔티티 레졸루션이며 별도의 난제다. 여기 손대면 프로젝트가 거기서 끝난다. v1은 **통합 스키마 + 통합 정렬 + 출처 표시**까지만. |
| **로그인 뒤 데이터** | 계정 위임·세션 유지·2FA가 따라오고, 그 순간 제품의 절반이 인증 관리가 된다. 기술적으로 범위 밖. |
| **대규모 크롤링 · 프록시 우회** | 본질이 차단 대응이라 강점이 전혀 다른 곳에 있다. 별도 사업이다. |
| **팀 권한 · SSO · 감사 로그** | 민재형 고객이 실제로 올 때까지 만들지 않는다. 이번 5일에는 특히 아니다. |
| **무한 페이지네이션** | 소스당 수집 페이지 수에 상한을 둔다(기본 3페이지). 상한을 푸는 건 별도 결정. |
| **모바일 전용 화면** | 반응형으로 안 깨지는 정도까지만. 전용 레이아웃은 만들지 않는다. |

### 기술적 예의 (법적 고려가 아니라 안정성 고려)

프로젝트성이므로 법적 검토는 이번 범위에서 다루지 않는다. 다만 **차단당하면 데모가 죽는다.** 그래서 다음은 지킨다 — 소스별 요청 간격 제한, 식별 가능한 User-Agent, 캐시 TTL을 둬서 같은 페이지를 반복해 때리지 않기, 원문 링크 항상 보존. 이건 예의라기보다 **수집 안정성 설계**다.

# Part II — 기술

> 이 파트는 교체 가능하다. 조건이 추가되면 여기와 부록 B만 고친다.

## 7. 기술 원칙

> 다섯 개의 판단이 나머지를 결정한다

### ① LLM은 런타임이 아니라 컴파일러다
요청마다 LLM에 HTML을 던져 파싱시키면 느리고 비싸고 매번 결과가 달라져 서비스가 성립하지 않는다. 대신 스키마와 샘플 페이지를 주고 **추출 방법을 한 번 생성해 저장**한다. 이후 실행은 전부 결정론적 코드로 돌아간다. LLM은 어댑터를 만들 때와 고칠 때만 호출된다.

**Gemini 무료 티어를 쓰는 이번 프로젝트에서 이 원칙은 선택이 아니라 필수다.** 소스 하나당 생성 1~2회, 자가 치유 발생 시 1~2회. 사용자가 API를 아무리 많이 호출해도 LLM 호출은 0이다.

### ② LLM이 만드는 것은 코드가 아니라 선언적 스펙이다 (v2 신설 · 핵심 변경)

원 기획안은 "추출 코드를 생성해 저장"이라고 했다. **v2에서는 코드 대신 JSON 스펙을 생성한다.** 이유는 네 가지다.

| 이유 | 코드 생성 | 스펙 생성 |
|---|---|---|
| 실행 안전성 | LLM이 쓴 임의 코드를 서버에서 실행 → 샌드박스(isolated-vm 등)가 필요 | 우리가 만든 해석기가 돌림. 코드 실행이 없음 |
| 검증 | 코드가 뭘 하는지 정적으로 판단 어려움 | 스펙 필드를 그대로 검사 가능 |
| 자가 치유 | 두 버전의 코드 diff가 사람이 못 읽음 | "이 필드의 경로가 A→B로 바뀜"으로 읽힘 |
| 롤백 | 코드 저장·버전 관리가 무거움 | JSON 한 덩어리 |

5일이라는 기간에서 샌드박스 구축은 순수한 손실이다. 스펙 방식은 그 비용을 0으로 만든다. 표현력 부족은 **제한된 변환 파이프라인**으로 메운다 (11장).

### ③ 내부 JSON 엔드포인트를 먼저 찾는다
목록형 사이트 상당수는 프론트에서 자기 내부 API를 호출해 JSON을 받아온다. 그것을 찾으면 HTML 구조 변경에 강하고, 페이지네이션이 깔끔하고, 파싱 스펙이 열 줄이다. 어댑터 생성기의 **1단계를 내부 JSON 탐지**로 두고 실패 시 HTML 파싱으로 폴백한다. 이 순서 하나가 유지보수 비용의 상당 부분을 줄인다.

**헤드리스 브라우저를 쓰기로 한 결정(P3)이 이 원칙을 강화한다.** 브라우저로 페이지를 열면 네트워크 요청을 그대로 관찰할 수 있으므로, 내부 API를 "추측"하는 게 아니라 "목격"하게 된다. 헤드리스는 JS 렌더링용이 아니라 **내부 API 탐지용으로 먼저 쓰인다.**

### ④ 부분 성공이 1급 시민이다
"전부 성공 아니면 실패"로 만들면 소스 하나가 깨질 때마다 서비스 전체가 죽는다. 응답 자체에 소스별 상태를 싣는다.

```json
{ "items": [ … ],
  "sources": {
    "k-startup.go.kr":  { "status": "ok",      "items": 3 },
    "bizinfo.go.kr":    { "status": "ok",      "items": 3 },
    "thinkcontest.com": { "status": "healing", "items": 2, "age": "6h" }
  },
  "schema_version": 3 }
```

이 구조 덕분에 **소스 하나짜리로 런칭해도 쓸모가 있고, 하나씩 붙일 때마다 선형으로 좋아진다.** 완성도가 아니라 커버리지가 늘어나는 구조라 중간에 멈춰도 제품이다. 크롤러 프로젝트가 대부분 죽는 이유는 "다 되어야 쓸 수 있게" 만들기 때문이다.

### ⑤ 스키마가 곧 검증기다
③의 타입 정보가 있으므로 별도의 헬스체크를 만들 필요가 없다. 수집 결과를 스키마에 통과시키는 것만으로 드리프트가 감지된다. 경쟁 제품이 "AI가 알아서 파싱해줍니다"를 파는 동안 이 제품은 **"깨지면 알아서 고칩니다"** 를 판다.

### 데이터 모델 (최소)

**Collection** — 스키마 + 소스 목록 + 엔드포인트 하나 · **Source** — 호스트와 진입 URL · **Adapter** — (Source × Schema) 추출 스펙, 버전 관리 · **Run** — 실행 기록과 검증 결과 · **Subscription** — 스케줄과 전달 채널. 사용자에게 노출되는 명사는 Collection 하나뿐이다. (→ 보장선 B2)

## 8. 추천 기술 스택

전제 P1~P8에서 도출된 조합이다. 각 선택의 근거와 교체 조건은 부록 B(ADR)에 있다.

### 언어와 런타임

| 영역 | 선택 | 근거 |
|---|---|---|
| 언어 | **TypeScript 단일** | 스키마 타입 하나를 프론트·수집기·API 응답·MCP 도구 정의가 전부 공유한다. 이 제품은 "타입이 곧 제품"이라 언어를 쪼개면 정의가 두 군데로 갈라진다 |
| 런타임 | **Node.js 22 LTS** | Playwright·MCP SDK·BullMQ가 전부 1급 지원. Bun은 Playwright 조합에서 아직 변수 |
| 패키지 | **pnpm workspace** | 모노레포. `packages/core`를 네 앱이 공유 |

### 앱 구성

```
apps/
  web      Next.js 15 (App Router)   화면 + 인증 + 관리 API + 공개 v1 API
  worker   Node 프로세스              수집 · 어댑터 컴파일 · 검증 · 자가 치유 · 구독 발송
  mcp      Node 프로세스              MCP Streamable HTTP 서버
packages/
  core     타입 · 스키마 정의 · 정규화 파서 · 어댑터 스펙 해석기 · 검증기
```

`core`가 웹과 워커와 MCP 모두에 들어간다. **어댑터 스펙 해석기가 여기 있는 게 중요하다** — 화면의 "미리보기"와 워커의 "정기 수집"이 같은 코드로 돌아야 미리보기가 거짓말을 하지 않는다.

### 주요 라이브러리

| 용도 | 선택 | 비고 |
|---|---|---|
| 화면 | Next.js 15 + React 19 | App Router. 서버 컴포넌트로 표 렌더 |
| UI | Tailwind + shadcn/ui | 5일에 디자인 시스템을 짤 시간이 없음 |
| 표 | TanStack Table | 정렬·필터를 클라이언트에서 즉시 |
| DB | **PostgreSQL 16** | 아이템은 JSONB, 검색은 GIN 인덱스. 별도 검색엔진 불필요 |
| ORM | **Drizzle ORM** | 스키마가 TS 타입 그대로. 마이그레이션 사이클이 짧아 5일에 유리 |
| 큐/스케줄 | **BullMQ + Redis** | repeatable job으로 크론 대체. 재시도·동시성 제한·소스별 rate limit을 공짜로 얻음 |
| 인증 | **Auth.js (NextAuth v5)** + Google | P4. Drizzle 어댑터 사용 |
| 브라우저 | **Playwright (Chromium)** | P3. 네트워크 관찰이 목적 |
| 정적 파싱 | **cheerio** | HTML 폴백 경로 |
| LLM | **Gemini API** (`gemini-2.5-flash` / `-pro`) | P6. 긴 HTML을 통째로 넣기 좋고 구조화 출력(responseSchema) 지원 |
| MCP | `@modelcontextprotocol/sdk` | Streamable HTTP transport |
| 웹훅/메일 | fetch + **Resend** | P7. 웹훅은 의존성 0, 이메일만 외부 |
| 로그 | pino + `runs` 테이블 | 사용자에게 보여줄 로그는 DB에, 디버그는 stdout |

### LLM 모델 배분 (비용 제약 대응)

| 호출 지점 | 모델 | 빈도 |
|---|---|---|
| 어댑터 스펙 최초 생성 | `gemini-2.5-pro` | 소스 추가 시 1회 (실패 시 재시도 1회) |
| 두 번째 소스 필드 매핑 | `gemini-2.5-flash` | 소스 추가 시 1회 |
| 분류값 매핑 제안 | `gemini-2.5-flash` | 필요 시 |
| 자가 치유 재컴파일 | `gemini-2.5-pro` | 드리프트 발생 시 1~2회 |

**정기 수집·API 호출·MCP 호출 경로에는 LLM이 없다.** 사용자가 하루에 API를 만 번 불러도 Gemini 호출은 0이다. 이것이 원칙 ①의 실질적 효과다.

### 배포 (P5)

   │   ├─ api.example.com  → web:3000/api/v1/*
   │   └─ mcp.example.com  → mcp:3002

Caddy를 쓰는 이유는 설정 세 줄로 Let's Encrypt 자동 발급이 되기 때문이다. Nginx + certbot은 5일에서 순수한 손실이다.

## 9. 아키텍처

### 9-1. 컬렉션 생성 흐름 (첫 소스)

```
[URL 입력]
    │
    ▼
① PROBE  ─────────────────────────────────────────────
    1. 정적 GET → HTML 확보
    2. 인라인 JSON 스캔
       __NEXT_DATA__ / __NUXT__ / window.__INITIAL_STATE__
       <script type="application/ld+json"> (ItemList)
    3. 없으면 → Playwright로 열고 네트워크 응답 관찰
       content-type: application/json 이고
       배열 길이 ≥ 3 이고 원소 키가 반복되는 것을 후보로 수집
    4. 그래도 없으면 → DOM 반복 구조 탐지
       같은 구조 시그니처가 N회 반복되는 컨테이너를 찾음
    │
    │  ※ 후보 순위 판정: 페이지에 눈으로 보이는 텍스트와
    │    후보 데이터의 값이 얼마나 겹치는가.
    │    "이게 그 목록이 맞다"를 이 겹침률로 판정한다.
    ▼
② COMPILE  (Gemini · pro)
    입력: 후보 데이터 샘플 + 페이지 텍스트 + URL
    출력: 어댑터 스펙 (JSON) — 11장
    │
    ▼
③ EXECUTE  (packages/core 해석기 · LLM 없음)
    스펙대로 추출 → 아이템 배열
    │
    ▼
④ INFER SCHEMA
    필드명 정리 + 타입 판정 (date/money/text/link/enum/number)
    │
    ▼
⑤ NORMALIZE
    타입별 파서로 값 변환
    │
    ▼
[이미 채워진 표를 사용자에게]  ← 보장선 B3
```

### 9-2. 두 번째 소스 접합 (기능 ② · 제품의 정체성)

```
[두 번째 URL 입력]
    │
    ▼
① PROBE  (동일)
    │
    ▼
② MATCH  (Gemini · flash)
    입력: 후보 데이터 샘플 + **기존 컬렉션 스키마**
    지시: "기존 필드를 이 데이터에서 찾아라. 없으면 없다고 답하라"
    출력: 필드별 경로 매핑 + 확신도 + 못 찾은 필드 목록
    │
    ├─ 전부 찾음 → 바로 표에 합류
    │
    └─ 일부 못 찾음
         → 사용자에게 **그 필드만** 물어봄
           "이 사이트에서 '마감일'에 해당하는 값을 하나 복사해 붙여넣어 주세요"
         → 붙여넣은 값을 원본 데이터에서 역추적해 경로 확정
         → 스펙에 반영                        ← 보장선 B1
    │
    ▼
③ NORMALIZE + 분류값 매핑
    "기술개발" ↔ "R&D" 같은 enum 매핑을 제안하고 사용자가 한 번 확인
    │
    ▼
[하나의 표에 두 출처가 섞여 나옴 · 출처 뱃지로 구분]
```

**여기가 제품이 성립하는 지점이다.** ②MATCH가 "전부 찾음"을 자주 내야 이 제품을 쓸 이유가 있다. 사용자가 매번 다섯 필드를 붙여넣어야 한다면 그냥 손으로 하는 게 낫다.

### 9-3. 정기 수집과 자가 치유 (기능 ④)

```
[BullMQ repeatable job — 소스별 스케줄]
    │
    ▼
① EXECUTE  스펙 해석기로 추출
    │
    ▼
② VALIDATE  — 스키마가 곧 검증기 (원칙 ⑤)
    ├─ items == 0                          → 실패
    ├─ items가 직전 대비 50% 이하           → 드리프트 의심
    ├─ 필드별 null 비율이 기준선 대비 +30%p → 드리프트
    └─ 타입 파싱 실패율 > 20%               → 드리프트
    │
    ├─ 통과 ──→ items UPSERT
    │            신규 판정: (source_id, external_key) 최초 등장 = first_seen_at
    │            변경 판정: content_hash 변화
    │            → 구독 발송 큐로
    │
    └─ 드리프트 ──→ ③ HEAL
                     │
                     ▼
         해당 소스만 status='healing' 으로 격리
         (나머지 소스는 계속 정상 응답 · 원칙 ④)
         마지막 성공 데이터는 계속 서빙하되 age 표시
                     │
                     ▼
         재컴파일 (Gemini · pro)
         입력: 현재 스펙 + 새 페이지 샘플 + **무엇이 깨졌는지**
              ("deadline 필드가 92% null입니다. 이전 경로는 $.reqstEndDe")
         출력: candidate 스펙
                     │
                     ▼
         candidate로 추출 → 재검증
         + 직전 성공 run의 아이템과 겹침률 확인 (엉뚱한 목록을 잡았는지)
                     │
         ┌───────────┴────────────┐
         ▼                        ▼
     통과                      실패 (재시도 1회 후에도)
     새 버전 승격               status='needs_attention'
     이전 버전 보존(롤백 가능)   화면에 상태 문구로 표시  ← 보장선 B4
     run 로그에 "자동 복구"      "이 사이트 구조가 바뀐 것 같아요"
```

**자동 복구를 로그로 쌓아 보여주는 게 기능의 절반이다.** 조용히 고치면 사용자는 이 제품이 무엇을 해주는지 영원히 모른다. 컬렉션 화면에 "이번 달 자동 복구 N회"를 상시 노출한다.

### 9-4. 구독 발송 (P7)

```
[items UPSERT에서 신규 아이템 발생]
    │
    ▼
subscriptions 조회 (컬렉션별 · 필터 조건 포함)
    │
    ▼
스케줄 확인 — 즉시 발송이 아니라 정해진 시각에 묶어 보냄
    │
    ▼
DELIVER  ── 채널 추상화 ──┬─→ webhook   fetch POST (JSON)      ← 먼저 만듦
                          └─→ email     Resend (HTML 템플릿)   ← 이어서 붙임
    │
    ▼
deliveries 기록 (재발송·중복 방지)
```

채널을 처음부터 인터페이스로 뺀다. 웹훅과 이메일이 같은 "무엇을 보낼지" 로직을 공유하고, 다른 건 "어떻게 보낼지"뿐이다. 이렇게 하면 P7의 "웹훅 먼저, 이메일 이어서"가 새 기능이 아니라 구현체 하나 추가가 된다.

## 10. 데이터 모델

```
users            Auth.js 표준 (id, email, name, image)
accounts         Auth.js 표준 (google provider)
sessions         Auth.js 표준

collections
  id, owner_id → users
  slug                    URL과 API 경로에 쓰임 (사용자가 정하거나 자동 생성)
  name
  schema_json             필드 정의 배열 (아래)
  schema_version          int — 필드 삭제/타입 변경 시 증가
  visibility              'private' | 'unlisted' | 'public'
  api_key_hash            공개 API 호출용 (private일 때 필수)
  created_at, updated_at

  schema_json 구조:
    [{ key: "deadline",
       label: "마감일",
       type: "date",
       required: false,
       mapping: null }              // enum일 때만 { "R&D": "rnd", "기술개발": "rnd" }
     …]

sources
  id, collection_id → collections
  host, entry_url
  status                  'ok' | 'healing' | 'needs_attention' | 'paused'
  schedule                cron 표현식 (기본 하루 1회)
  last_run_at, last_ok_at
  fetch_mode              'json' | 'html' | 'browser'   ← 어느 경로로 뚫렸는지

adapters
  id, source_id → sources
  version                 int
  spec_json               어댑터 스펙 (11장)
  origin                  'llm' | 'heal' | 'human'
  status                  'active' | 'candidate' | 'retired'
  validation_json         이 버전이 통과한 검증 결과 (승격 근거)
  created_at

items
  id, collection_id, source_id
  external_key            소스 내 고유 식별자 (원문 링크 또는 원본 id)
  data_json               정규화된 값 — 스키마 필드 키 그대로
  raw_json                원본 조각 (원문 대조용)
  provenance_json         필드별 원본 경로 — { "deadline": "$.reqstEndDe" }
  content_hash            변경 감지용
  first_seen_at           신규 판정 기준
  last_seen_at
  UNIQUE (source_id, external_key)

runs
  id, source_id, adapter_id
  started_at, finished_at
  status                  'ok' | 'drift' | 'healed' | 'failed'
  items_found, items_new
  validation_json         필드별 null 비율, 타입 실패율 등
  error_summary           사용자에게 보여줄 상태 문구 (내부 용어 금지 · B4)

subscriptions
  id, collection_id, user_id
  channel                 'webhook' | 'email'
  target                  URL 또는 이메일 주소
  filter_json             구독 조건 (표에서 건 필터 그대로)
  schedule                cron
  last_sent_at

deliveries
  id, subscription_id
  item_ids[], sent_at, status
```

### 몇 가지 판단

- **`items`를 컬렉션별 테이블로 쪼개지 않는다.** JSONB 하나로 받고 `data_json`에 GIN 인덱스. 5일 규모에서 동적 테이블 생성은 순수한 부채다.
- **`external_key`가 신규 판정의 전부다.** 이게 불안정하면(예: 매번 바뀌는 세션 파라미터가 링크에 붙는 사이트) 매 수집마다 전부 신규가 되어 구독이 스팸이 된다. 어댑터 스펙에 `dedupe_key` 필드를 두어 LLM이 안정적인 키를 고르게 하고, 못 고르면 정규화된 title 해시로 폴백한다.
- **`provenance_json`이 원문 대조의 실체다.** 스펙에 이미 경로가 있으므로 저장 비용이 거의 없다. 화면에서 값에 마우스를 올리면 `raw_json`의 해당 경로를 꺼내 보여준다.

## 11. 어댑터 스펙 (핵심 설계 · 원칙 ②)

LLM은 코드가 아니라 이 JSON을 생성한다. `packages/core`의 해석기가 이것을 읽어 실행한다.

### JSON 모드 (내부 API를 찾은 경우)

```json
{
  "spec_version": 1,
  "fetch": {
    "mode": "json",
    "url": "https://www.k-startup.go.kr/api/pbanc/list?page={page}&size=50",
    "method": "GET",
    "headers": { "Accept": "application/json" }
  },
  "list": "$.data.items[*]",
  "dedupe_key": "$.pbancSn",
  "fields": {
    "title":        { "path": "$.pbancNm",     "type": "text" },
    "organization": { "path": "$.jrsdInsttNm", "type": "text" },
    "deadline":     { "path": "$.reqstEndDe",  "type": "date",
                      "transform": [ { "op": "date_parse", "formats": ["YYYYMMDD", "YYYY.MM.DD"] } ] },
    "amount":       { "path": "$.sportAmount", "type": "money",
                      "transform": [ { "op": "regex_extract", "pattern": "[\\d,]+" },
                                     { "op": "number_parse" },
                                     { "op": "multiply", "by": 1000 } ] },
    "link":         { "path": "$.pbancSn",     "type": "link",
                      "transform": [ { "op": "template", "value": "https://www.k-startup.go.kr/web/contents/detail?sn={value}" } ] }
  },
  "pagination": { "kind": "page_param", "param": "page", "start": 1, "max_pages": 3 }
}
```

### HTML 모드 (폴백)

```json
{
  "spec_version": 1,
  "fetch": { "mode": "html", "url": "https://thinkcontest.com/contest/list?p={page}" },
  "list": "css:.contest-list > li",
  "dedupe_key": "css:a@href",
  "fields": {
    "title":    { "path": "css:.tit",  "type": "text" },
    "deadline": { "path": "css:.date", "type": "date",
                  "transform": [ { "op": "regex_extract", "pattern": "\\d{4}[.-]\\d{2}[.-]\\d{2}" },
                                 { "op": "date_parse" } ] },
    "link":     { "path": "css:a@href", "type": "link",
                  "transform": [ { "op": "absolute_url" } ] }
  },
  "pagination": { "kind": "next_link", "path": "css:a.next@href", "max_pages": 3 }
}
```

### browser 모드

`fetch.mode`가 `"browser"`이면 Playwright로 열고 `wait_for`(셀렉터 또는 networkidle) 후 DOM을 잡는다. 나머지 구조는 HTML 모드와 동일하다. 무한 스크롤은 `pagination.kind: "scroll"`에 `times`를 둔다.

### 변환 연산자 (닫힌 집합)

임의 코드 실행이 없으므로 표현력은 이 목록이 전부다. 목록형 사이트에서 실제로 필요한 것만 넣었다.

| op | 용도 |
|---|---|
| `trim`, `collapse_space` | 공백 정리 |
| `regex_extract` | 패턴으로 잘라내기 |
| `replace` | 치환 |
| `split` + `index` | 구분자로 자르고 n번째 |
| `date_parse` | 포맷 후보 배열로 시도. `D-7`, `상시`, `~2026-08-21` 같은 한국 목록 사이트 관용 표현 포함 |
| `number_parse` | 콤마·단위 제거 후 숫자 |
| `multiply` | 단위 승수 (천원 → ×1000, 만원 → ×10000, 억 → ×100000000) |
| `absolute_url` | 상대경로 → 절대 URL |
| `template` | `{value}`를 끼워 URL 조립 |
| `map` | enum 값 매핑 (`"기술개발" → "rnd"`) |
| `default` | 실패 시 기본값 |
| `join` | 배열을 문자열로 |

**여기 없는 변환이 필요하면 연산자를 추가한다. 코드 실행을 허용하지 않는다.** 이 선이 무너지면 샌드박스가 필요해지고, 그 순간 5일 안에 끝나지 않는다.

### 스펙 검증 (실행 전)

LLM이 만든 스펙은 실행 전에 형태 검사를 통과해야 한다 — `fetch.url`이 사용자가 준 호스트와 같은가, `list` 경로가 유효한 문법인가, 알 수 없는 `op`가 있는가, `max_pages`가 상한 이내인가. 통과 못 하면 오류 내용을 붙여 재생성 1회. 이건 프롬프트 신뢰가 아니라 계약 검사다.

## 12. API · MCP 계약

### REST API

```
GET /v1/{collection}
```

| 파라미터 | 예시 | 비고 |
|---|---|---|
| 필드 필터 | `?category=rnd&organization=창업진흥원` | 스키마 필드 키가 그대로 파라미터 |
| 범위 | `?deadline_gte=2026-08-01&amount_lte=100000000` | date/number/money 타입에만 |
| 정렬 | `?sort=deadline` / `?sort=-amount` | `-`가 내림차순 |
| 페이지 | `?limit=50&cursor=…` | 커서 기반 |
| 검색 | `?q=창업` | text 타입 필드 전체 대상 |
| 출처 | `?source=k-startup.go.kr` | |
| 신규만 | `?since=2026-07-20` | `first_seen_at` 기준 |
| 원문 | `?include=provenance` | 필드별 원본 조각 포함 |

응답은 원칙 ④의 형태를 그대로 따른다 — `items`, `sources`, `schema_version`. **`sources`는 옵션이 아니라 항상 포함된다.**

인증: `visibility`가 `private`이면 `Authorization: Bearer {api_key}`. `unlisted`는 추측 불가 slug만으로 접근 가능. `public`은 무인증.

스키마 변경: 필드 삭제 또는 타입 변경 시 `schema_version`이 오르고, 화면에서 breaking change를 경고한다. 이전 버전 응답은 유지하지 않는다(5일 범위). 대신 경고를 명확히 한다.

### MCP 서버

```
https://mcp.example.com/{collection}      (Streamable HTTP)
인증: Authorization: Bearer {api_key}
```

도구는 컬렉션 스키마에서 **자동 생성**된다. 필드명과 타입이 도구 설명에 들어가므로 클라이언트 LLM이 별도 학습 없이 쓴다.

| 도구 | 설명 |
|---|---|
| `list_items` | 필터·정렬·개수 제한. 파라미터가 스키마 필드에서 생성됨 |
| `search_items` | 자연어 질의 → text 필드 검색 |
| `get_schema` | 이 컬렉션에 어떤 필드가 있는지 |
| `get_sources_status` | 소스별 상태와 마지막 갱신 시각 (원칙 ④가 여기서도 노출) |

**보장선 B7의 구현:** 컬렉션 화면에 "AI에 연결" 버튼 하나. 누르면 MCP 주소와 키가 합쳐진 한 줄이 클립보드에 복사되고, 커넥터 설정에 붙여넣으라는 안내 한 장이 뜬다. 설정 파일 편집이나 로컬 설치를 요구하지 않는다.

# Part III — 실행

## 13. 5일 관문(Gate) 로드맵

### 이 로드맵의 규칙

1. **작업량과 속도를 추정하지 않는다.** "하루에 이만큼 할 수 있다"는 계산은 이 문서에 없다. 각 관문에는 통과 판정 조건만 있다.
2. **관문은 말이 아니라 화면으로 판정한다.** 구두 보고가 아니라 실제로 돌려서 본다.
3. **판정값은 통과/미통과 둘뿐이다.** "거의 됨"은 미통과다.
4. **미통과면 그 자리에서 강등 규칙을 발동할지 결정한다.** 다음 관문으로 부채를 넘기지 않는다. 강등은 실패가 아니라 설계된 경로다.
5. **하루의 시작에 다음 관문의 통과 조건을 소리 내어 확인하고, 하루의 끝에 판정한다.** 이 두 번 외에는 서로의 진척을 묻지 않는다.

### 관문 요약

| 관문 | 이름 | 한 줄 판정 |
|---|---|---|
| **G0** | 계약 고정 | 가짜 데이터로 두 트랙이 서로를 안 기다린다 |
| **G1** | URL 하나가 아이템이 된다 | 그 자리에서 정한 낯선 URL에서 아이템이 나온다 |
| **G2** | 두 번째 소스가 붙는다 | 두 출처가 한 표에 같은 형식으로 섞인다 |
| **G3** | 계속 돈다 | 일부러 깨뜨려도 혼자 고치고, 나머지는 산다 |
| **G4** | 배포 · MCP · 낯선 사람 | 도메인에서 처음 본 사람이 혼자 성공한다 |
| **G5** | 데모 | 끊김 없이 한 번에 녹화된다 |

---

### G0 — 계약 고정 · Day 1 시작 (두 사람 공동)

이 관문만은 둘이 같이 붙는다. 여기서 만든 계약이 남은 4일의 병렬성을 결정한다.

**통과 판정**

- `packages/core`에 Collection / Source / Adapter / Item / Run / Subscription 타입이 있고, 어댑터 스펙 타입(11장)과 변환 연산자 목록이 정의되어 있다
- DB 마이그레이션이 돌고, 시드 스크립트가 **가짜 컬렉션 1개 + 소스 2개 + 아이템 20개**를 넣는다
- 그 시드 데이터로 `GET /v1/{collection}`이 7장 ④의 응답 형태를 그대로 뱉는다 — `items`, `sources`, `schema_version`. **데이터는 전부 가짜여도 된다**
- 트랙 B가 트랙 A의 코드 없이 화면을 만들 수 있고, 트랙 A가 트랙 B의 화면 없이 파이프라인을 만들 수 있다

**이 관문이 여는 것** — 두 트랙의 완전 병렬화

**강등 규칙** — 없다. 이 관문은 강등할 수 없다. 못 넘으면 넘을 때까지 둘이 붙는다. 여기를 대충 넘기면 G2 합류에서 이틀치가 날아간다.

---

### G1 — URL 하나가 아이템이 된다 · Day 1 종료

**트랙 A 통과 판정**

- **판정하는 자리에서 처음 고른** 목록 URL 3개를 넣었을 때, 최소 2개에서 아이템 5개 이상이 추출된다 (미리 뚫어둔 URL로 판정하지 않는다 — P2)
- probe가 어느 경로로 뚫렸는지가 로그에 구분돼 남는다: 인라인 JSON / 네트워크 관찰 / DOM 반복 구조 / 브라우저 렌더
- 추출된 필드에 타입이 붙고, 날짜와 금액이 정규화된 값으로 나온다

**트랙 B 통과 판정**

- 구글 로그인이 되고, 로그인 후 "내 컬렉션 목록" 화면이 있다
- 컬렉션 상세에서 시드 데이터가 표로 렌더되고 정렬·필터가 동작한다
- 보장선 **B5** 점검: API URL이 화면에 있되 접혀 있다

**강등 규칙** (트랙 A가 미통과일 때, 위에서부터 순서대로)

1. 브라우저 probe를 뒤로 미룬다 — 인라인 JSON + 정적 HTML만으로 G1을 다시 판정
2. 그래도 미통과면 DOM 반복 구조 탐지를 버리고 인라인 JSON + 네트워크 관찰만 남긴다
3. 그래도 미통과면 대상을 미리 뚫어둔 3곳으로 좁히고, 임의 URL은 화면에서 "실험" 상태로 표시한다 (P2 후퇴 — 여기까지 오면 제품 주장이 약해지므로 G5 발표에서 이 한계를 명시한다)

---

### G2 — 두 번째 소스가 붙는다 · Day 2 종료 (첫 합류 지점)

**여기까지가 원 기획안의 v1이고, 제품이 성립하는 지점이다.**

**통과 판정**

- 서로 다른 호스트 2곳의 아이템이 **하나의 표**에 섞여 나오고, 출처 뱃지로 구분된다
- 두 번째 소스의 필드가 기존 스키마에 **자동으로 매핑**되고, 못 찾은 것만 사용자에게 물어본다
- 사용자는 **값을 붙여넣어** 그 필드를 해결한다 — 셀렉터를 입력하지 않는다 (보장선 B1)
- 날짜와 금액이 두 소스에서 같은 형식으로 나온다
- `GET /v1/{collection}`이 실제 데이터로 응답하고, 필터·정렬·페이지가 동작하며, `sources`에 소스별 상태가 들어 있다
- 값에 마우스를 올리면 원문 조각이 보인다 (원문 대조)

**이 관문이 여는 것** — 이 아래로는 전부 "있으면 더 좋은 것"이다. G2를 넘으면 최악의 경우에도 발표할 물건이 있다.

**강등 규칙**

1. 자동 매핑의 확신도 기준을 낮춰 더 많이 시도하고, 틀리면 사용자가 고치는 경로를 넓힌다
2. 그래도 미통과면 자동 매핑을 포기하고 **전 필드를 붙여넣기로** 받는다 (기능 ②의 주장은 약해지지만 "두 소스가 하나의 표"는 지킨다. 보장선 B1은 유지된다)
3. 원문 대조를 G4로 미룬다 (마지막 수단 — 5장의 신뢰 계층이 약해짐)

---

### G3 — 계속 돈다 · Day 3 종료

**트랙 A 통과 판정 (자가 치유)**

- 스케줄 수집이 사람 손 없이 돌고, 신규 항목이 기존 항목과 구분된다
- 소스 하나를 **일부러 깨뜨렸을 때**(예: 스펙의 경로를 손으로 틀리게 바꾸거나 대상 페이지의 로컬 사본을 변형) 검증이 그걸 잡아낸다
- 깨진 소스만 격리되고, **나머지 소스는 계속 정상 응답한다** (원칙 ④)
- 자가 치유 잡이 새 스펙을 만들어 재검증을 통과하면 자동 승격되고, 이전 버전이 롤백 가능하게 남는다
- 컬렉션 화면에 "자동 복구 N회"가 보인다

**트랙 B 통과 판정 (피드 + 구독)**

- 읽기 피드 화면이 있고, "새로 올라온 것"과 "마감 임박"이 구분된다
- 웹훅 구독을 걸면 **신규 항목만** 담긴 페이로드가 1회 전송에 성공한다
- 발송 채널이 인터페이스로 추상화되어 있다 (이메일 구현체를 추가할 자리가 비어 있다)
- 보장선 **B4** 점검: 깨진 소스가 화면에서 빨간 에러가 아니라 상태 문구로 보인다

**강등 규칙**

1. 자동 승격을 빼고 **감지 + 격리 + 사람 호출**까지만 한다. 재컴파일 버튼을 사람이 누른다 (기능 ④의 절반. 화면 상태 표시와 "복구 N회" 로그는 유지 — 데모에서 보여줄 것이 남는다)
2. 그래도 미통과면 검증(드리프트 감지)까지만 하고 치유를 버린다. **이때 5장의 "사수해야 할 셋" 중 하나가 무너지므로, G5 발표에서 이 부분을 미완으로 명시한다**
3. 구독 쪽이 미통과면 스케줄 발송을 버리고 "즉시 발송"만 남긴다

---

### G4 — 배포 · MCP · 낯선 사람 · Day 4 종료

**통과 판정**

- 도메인에 HTTPS로 떠 있고, 재부팅해도 컨테이너가 다시 뜬다
- **이 프로젝트를 모르는 사람**이 도메인에 접속해서: 구글 로그인 → URL 2개 붙여넣기 → 컬렉션 생성 → 표 확인까지 **설명 없이** 도달한다
  - 이 판정이 원 기획안 10장의 사용자 테스트를 대신한다 (P10). 한 명이면 충분하다 — 통과/미통과만 보면 되고, 막히는 지점이 어디인지는 옆에서 보면 안다
- MCP 주소를 커넥터에 붙여넣으면 "이번 주 마감 뭐 있어?"에 실제 아이템으로 답한다
- 이메일 구독이 붙는다 (P7의 후반)
- 보장선 **B1~B7 전수 점검**. 하나라도 위반이면 미통과

**강등 규칙**

1. 이메일 구독을 버린다 (웹훅만 남김 — P7의 "이어서"가 안 온 것)
2. MCP를 배포된 HTTP 서버 대신 **로컬 stdio + 설치 안내 한 줄**로 낮춘다 (보장선 B7이 깨지므로, 데모에서는 개발자 경로임을 명시한다. **이건 뼈아픈 강등이다** — 3장에서 MCP를 가장 차별적이라고 했고 그 이유가 비개발자 접근이었다)
3. 낯선 사람 테스트를 통과 못 하면, 막힌 지점 하나만 고치고 나머지 기능 작업을 전부 멈춘다 (보장선이 기능보다 우선한다 — 5장 냉정한 우선순위)

---

### G5 — 데모 · Day 5 종료 (두 사람 공동)

**통과 판정**

- **끊김 없이 한 번에 녹화한** 데모 영상이 있다. 편집으로 실패를 가리지 않는다
- 영상에 네 표면이 모두 나온다: 표 · 읽기/구독 · API 응답 · MCP 대화
- 영상에 자가 치유가 나온다 (소스를 깨고 → 상태가 바뀌고 → 복구되는 장면)
- 발표 자료가 있고, **강등한 것이 있다면 그것을 숨기지 않고 적는다**

**강등 규칙** — 없다. 여기 도달하지 못하면 직전 관문 상태 그대로 녹화한다. 없는 기능을 녹화 트릭으로 만들지 않는다.

### 관문 간 의존 관계

```
G0 ─┬─→ G1(A) ──→ G2 ──→ G3(A) ──→ G4 ──→ G5
    └─→ G1(B) ──┘        G3(B) ──┘

G0  두 사람 공동 (병렬화의 전제)
G1  A와 B가 각자 독립 — 서로 안 봄
G2  첫 합류. A의 파이프라인이 B의 표에 실제 데이터를 넣음
G3  다시 갈라짐. A는 자가 치유, B는 피드·구독
G4  두 번째 합류. 배포와 MCP는 둘이 붙음
G5  공동
```

**G2와 G4가 합류 지점이다.** 이 두 곳에서만 서로의 결과물이 필요하고, 나머지는 G0에서 고정한 계약으로 각자 간다.

## 14. 역할 분담

두 사람 모두 Claude Max 5x를 쓴다(P8). 코드 생산이 병목이 아니므로, **분담의 기준은 "누가 더 빨리 짜는가"가 아니라 "어디에서 사람의 판단이 필요한가"** 다. 판단이 필요한 지점을 두 사람에게 겹치지 않게 나눈다.

| | **트랙 A — 파이프라인** | **트랙 B — 표면** |
|---|---|---|
| 담당 | probe, 어댑터 컴파일, 스펙 해석기, 정규화, 검증, 자가 치유, 스케줄러 | 인증, 컬렉션 화면, 표, 피드, REST API, MCP, 구독 발송 |
| 사람이 판단할 것 | 후보 목록이 맞는가 / 정규화가 맞는가 / 드리프트 기준선이 적절한가 / 치유 결과를 승격해도 되는가 | 보장선 B1~B7이 지켜지는가 / 접힘의 기본값이 맞는가 / 상태 문구가 사람 말인가 |
| 주 관문 | G1(A), G3(A) | G1(B), G3(B) |
| 공동 | G0, G2, G4, G5 | |

### 트랙 계약 (G0에서 고정하고 이후 바꾸지 않는다)

바꿔야 할 일이 생기면 **양쪽이 같이 있을 때만** 바꾼다. 혼자 바꾸면 상대 트랙이 조용히 깨진다.

1. `packages/core`의 타입 정의 (Collection, Source, Adapter, Item, Run, Subscription, 어댑터 스펙)
2. DB 스키마와 마이그레이션
3. `GET /v1/{collection}` 응답 형태 — `items` / `sources` / `schema_version`
4. 시드 스크립트가 만드는 가짜 데이터 (B가 A를 기다리지 않게 하는 장치)
5. 상태 값의 집합 — `ok` / `healing` / `needs_attention` / `paused`

### Claude 활용에 대한 실무 노트

- **어댑터 스펙의 JSON Schema를 먼저 확정하고 그것을 프롬프트에 넣는다.** Gemini의 구조화 출력(`responseSchema`)에 그대로 물린다. 스펙 타입이 코드·프롬프트·검증의 단일 출처가 된다
- **정규화 파서와 변환 연산자는 테스트를 먼저 쓴다.** 여기는 실제 사이트의 지저분한 실제 값(`~2026-08-21`, `최대 100,000천원`, `D-7`, `상시모집`)을 케이스로 모아두면 생성 품질이 크게 오른다. 실제 값 수집은 G1 probe 결과에서 그대로 나온다
- **두 사람이 같은 파일을 만지지 않게 트랙 경계를 디렉터리 경계와 일치시킨다.** `apps/worker`는 A, `apps/web`·`apps/mcp`는 B, `packages/core`는 G0 이후 변경 시 상호 통보

| 리스크 | 내용 | 대응 |
|---|---|---|
| **임의 URL의 성공률** | P2를 택한 대가. 목록 구조가 특이한 사이트에서 probe가 엉뚱한 배열을 잡을 수 있다 | 후보 순위를 "화면에 보이는 텍스트와의 겹침률"로 판정 (9-1). 그래도 안 되면 G1 강등 규칙 |
| **`external_key` 불안정** | 링크에 세션 파라미터가 붙는 사이트에서 매 수집이 전부 신규가 되어 구독이 스팸이 된다 | 어댑터 스펙에 `dedupe_key`를 두고 LLM이 안정적인 키를 고르게 함. 폴백은 정규화 title 해시. **G3 판정에 "두 번 연속 수집 시 신규가 0인가"를 포함** |
| **Playwright가 VM을 잡아먹음** | 브라우저 인스턴스가 메모리를 먹어 다른 컨테이너가 죽는다 | 워커 동시성 1~2로 제한, 컨테이너 메모리 상한 설정, 브라우저는 작업 후 즉시 닫기. VM은 8GB 권장 |
| **Gemini 무료 티어 한도** | 자가 치유가 폭주하면 하루 한도를 넘긴다 | 소스별 치유 시도를 하루 N회로 제한. 초과 시 `needs_attention`으로 넘기고 사람 호출. **한도 초과가 서비스 정지가 아니라 상태가 되게 한다** (원칙 ④) |
| **G2를 못 넘김** | 제품이 성립하는 지점을 못 넘으면 남은 3일이 "한 사이트 스크래퍼"에 얹히는 기능이 된다 | G2를 Day 2 종료로 앞당겨 배치한 이유가 이것이다. 미통과 시 G3 이후 계획을 전부 재배치한다 |
| **보장선이 조용히 무너짐** | 기능을 붙이다 보면 "일단 셀렉터 입력창 하나만" 같은 타협이 들어온다 | B1~B7을 **G4의 전수 점검 항목**으로 못 박음. 위반이면 기능 작업을 멈추고 이걸 먼저 고친다 |
| **차별점 방어** | ①③⑤는 경쟁사가 금방 따라온다 | ②와 ④에 자원 집중. 특히 실사용 텔레메트리(실제 지연·에러율·복구 이력)는 정적 도구가 가질 수 없는 유일한 해자 |
| **데모 당일 대상 사이트가 바뀜** | 라이브 데모 중 소스가 깨진다 | **이건 리스크가 아니라 기능이다.** 깨지면 자가 치유가 도는 장면을 그대로 보여준다. 단 G5는 사전 녹화이므로 실패 시 재녹화 |

## 16. 열린 결정 (아직 안 정한 것)

기술 조건 추가가 예상되는 지점이다. 각 항목은 정해지면 부록 B의 ADR로 승격한다.

| # | 열린 질문 | 정해야 하는 시점 | 기본값 (안 정하면 이걸로 간다) |
|---|---|---|---|
| O1 | 도메인 이름 | G4 이전 | 미정 — 제품명 `endpointer`는 가칭 |
| O2 | 컬렉션 공개 범위의 기본값 | G2 | `unlisted` (추측 불가 slug, 무인증 조회) |
| O3 | 수집 주기의 기본값 | G3 | 하루 1회, 사용자가 컬렉션별로 변경 |
| O4 | 아이템 보존 기간 | G3 | 무제한 (5일 규모에서 문제되지 않음) |
| O5 | `raw_json` 저장 범위 | G2 | 아이템당 원본 객체 전체. 용량이 문제되면 필드 경로에 해당하는 조각만 |
| O6 | 스키마 v(n-1) 응답 유지 여부 | G4 | 유지하지 않음. breaking change 경고만 |
| O7 | 즐겨찾기를 컬렉션 안에 둘지 별도 컬렉션으로 만들지 | G3 | 컬렉션 안에 `starred` 플래그 |
| O8 | 여러 사용자가 같은 소스를 볼 때 수집을 공유할지 | 범위 밖 (v3) | 사용자별 독립 수집 |
